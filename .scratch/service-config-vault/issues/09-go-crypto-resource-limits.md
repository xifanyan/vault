## Question

若不用既有加密容器，Go 官方及 Go 密码扩展库有哪些成熟原语适合构成小型口令加密配置文件，其安全使用条件和认证前资源风险是什么？

依据 Argon2 规范、Go 官方包文档及源码，核查 Argon2id、scrypt、AES-GCM 与 XChaCha20-Poly1305 的实际接口、关键参数与随机量条件、附加认证数据能力、口令派生的内存与时间开销来源，以及如何在认证前限制不可信文件诱导的资源分配。

明确参数指导不等于本项目基准结果；区分可跨平台构建的源码事实、FIPS 认证与没有验证的运行时保证。列出对文件头、版本和加密载荷设计的约束，并比较自行组合原语相对复用既有容器增加的协议责任。每项事实引用第一方来源，不替用户选择算法或资源预算。

## Answer

已完成[Go 密码原语与资源上限研究](../research/go-crypto-resource-limits.md)，逐项链接规范、官方 API 与源码，区分 Argon2id/scrypt 的资源模型、GCM/XChaCha 的随机量与认证条件，以及自行维护文件协议的额外责任。

结论是必须在派生前限制不可信成本参数，不能把算法参数合法、官方参考配置或 Go 包存在等同于预算与平台保证。本研究不选择最终原语组合，也未对替代原语运行基准或跨平台测试。
