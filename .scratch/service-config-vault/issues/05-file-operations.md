## Question

如何使已有加密 vault 与独立解锁凭据能够直接复制到其他 Windows、Linux 或 macOS 主机使用，而不把复杂的文件协调、文件系统保证或部署协议变成前提？

沿用[既定加密格式](04-encrypted-file-format.md#answer)和[口令规则](03-passphrase-input.md#answer)，不因“keys”一词未经确认就切换加密模式。只明确普通文件使用、复制完成后打开，以及基本写入与错误边界。

此前的 [Windows 研究](10-windows-file-semantics.md)和 [Linux/macOS 研究](11-posix-file-semantics.md)保留作历史参考，不再是交付前置。

### 首轮使用边界确认

用户通过选项确认以下产品约束；平台原子性、刷新和崩溃保证仍待研究与后续讨论：

- Windows、Linux、macOS 分别支持 amd64 与 arm64，共六个目标组合；正式支持须有对应运行验收，不把交叉编译当成运行证明。

- 最终 vault 文件不能是符号链接或多重硬链接；先解析父目录真实路径，并要求目录不受不可信用户改写。
- 每台主机使用一个指定本机账户同时运行 CLI 和业务程序；默认只授权它访问 vault 与协调文件，管理员不属于隔离目标。各主机账户可不同，复制后按目标主机设置权限。

## Answer

### 核心交付与便携性

可迁移材料只有加密 vault 和独立解锁凭据文件，例如 `service.vault` 与 `service.pass`。这里的凭据沿用已确认的口令文件，不新增私钥模式或机器绑定密钥。

新主机只需具备兼容的 CLI 或 Go 集成，能够读取这两份文件，即可使用相同口令解锁并针对同一环境取得相同配置。文件名称和路径可以改变，不依赖源主机用户名、SID/UID、绝对路径、系统钥匙链或本地注册状态。

CLI 与 Go 的文件式入口显式接收凭据文件位置，共用同一口令文件适配器，再把实际口令交给解锁核心；不会要求业务调用方另写一套换行处理。底层格式、完整认证、配置层级及脱敏规则保持不变；不自动改写业务配置里由用户保存的主机地址或路径。

### 最简单的使用流程

1. 在一台主机通过 CLI 或可读写的 Go 库管理 vault；程序化修改在内存中进行，再显式保存。
2. 在没有并发修改或读取文件的时段，复制 vault 和所需解锁凭据到另一主机；复制完成后再打开或显式重新加载。
3. 按目标主机设置普通文件访问权限，使运行程序的账户能够读取，并保护凭据不被无关账户获取。

不要求受控安装、注册或导入命令，不生成必需的协调文件，不维护 NTFS/ext4/APFS 白名单。仍需使用对应系统的兼容程序及正常可访问的文件路径；不把这解释成所有特殊存储或旧系统都已验收。

### 写入和并发边界

同一个副本的修改和复制由操作者串行安排，包括避免同机多个写进程；不实现自动跨进程或跨主机协调，也不承诺并发覆盖不会丢失更新。

保留基本安全写入：在目标同目录写完新的密文临时文件，检查写入、刷新和关闭结果，再尝试系统文件替换，不原地截断正式 vault。错误如实返回，不增加自动重试、回滚或复杂提交状态机；若替换阶段失败，不声称原文件绝对未动，应重新打开核对。

程序从单次文件读取取得完整密文，完成读取后关闭文件句柄，再在内存中完整认证和解析；既有配置快照不自动改变。读取失败、复制不完整、错误口令或无效载荷均明确失败，不返回部分配置或伪造空配置。

不承诺三平台文件系统级原子切换、断电事务或介质故障恢复；不以共享/独占读写锁来掩盖这些边界。普通系统权限由部署方配置，不建立跨账户授权或自动修复目录 ACL 的额外机制。

### 凭据保护与验收目标

凭据作为独立文件可以迁移，不嵌入 vault、导出、日志或命令行明文参数。vault 与解锁凭据若同时泄露，持有者即可解密；部署方负责安全传输和保管。

验收重点是：在受支持的 Windows、Linux、macOS 程序之间复制同一 vault 和凭据后，成功解锁、得到相同层级解析结果，并能继续通过 CLI 管理及导出 JSON。修改口令后的旧副本边界仍沿用口令票据。
