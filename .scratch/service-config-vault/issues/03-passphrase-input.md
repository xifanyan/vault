## Question

在已确认隐藏交互输入、自动化使用标准输入或口令文件、Go 调用方显式提供口令的前提下，怎样定义可同时用于人工管理与无人值守服务的解锁契约？

需要与用户确定：

- 口令输入来源的显式选择、多个来源同时指定时的行为，以及非交互模式缺少口令时的失败方式。
- 标准输入被配置值占用时如何提供口令，避免两个输入共享同一通道产生歧义。
- 口令文件的内容编码、换行处理、空口令与 Unicode 处理规则，使不同主机得到相同的口令字节。
- 新建和更换口令时的确认流程，以及旧口令和新口令的输入组合；旧副本无法撤销的限制必须保留。
- CLI 与 Go 调用方对口令生命周期的责任，不承诺忘记口令后的恢复能力或进程内明文完全不可提取。

本票确定操作契约，不选择密码算法或实现交互提示。

## Answer

### 输入口令的来源

每份口令仅允许一个来源：隐藏终端输入、口令文件或标准输入。指定多个来源时报错，不设置优先级，也不在读取或验证失败后回退到其他来源。

未指定来源时，只有可交互终端可以提示输入；无人值守环境直接报错，不能等待终端或从其他通道猜测口令。显式选择终端输入也要求存在可交互终端，不把管道输入当成隐藏终端。

旧口令和新口令是两份独立输入，可以各自指定不同来源，但每份输入仍遵循来源互斥规则。CLI 来源选项、Go 的 `Open`、`Create` 与 `SaveWithCredentials` 见[接口契约](07-cli-go-contract.md#answer)。

### 标准输入的归属

一次操作的标准输入最多承载一个逻辑输入：配置值、旧口令、新口令或普通解锁口令之一。不设计多份秘密拼接或按行分隔的复用协议。

配置值已占用标准输入时，口令改由口令文件或可交互终端提供；更换口令时，旧口令和新口令也不能同时使用标准输入。冲突明确报错，不先消费部分输入再猜测其归属。

### 口令文本与跨平台一致性

所有口令内容采用有效 UTF-8，不接受开头的 BOM；拒绝空口令、包含 CR 或 LF 的多行内容以及 NUL 字符。除输入来源的行结束符处理外，前后空格和 Unicode 字符原样保留，不做裁剪、大小写转换或 Unicode 归一化。

CLI 与 Go 的文件式入口共用口令文件适配规则：只移除一个结尾的 LF 或 CRLF，之后仍有 CR 或 LF 就拒绝。CLI 显式选择标准输入时采用同样的单行规则；交互输入的终端行结束符不属于口令内容。

解锁核心接收实际口令内容，不移除空格或行尾；直接作为口令内容传入的换行会被拒绝。Go 文件式入口先使用同一文件适配器取得实际口令，再交给核心，不猜测环境变量或钥匙链。具体签名见[接口契约](07-cli-go-contract.md#answer)，输入适配后的 UTF-8 字节规则不变。

### 新建与更换口令

新建 vault 或更换口令时，交互式新口令输入两次并一致后才能继续。自动化从每份口令的显式来源读取一次，不额外提示或要求把同一秘密重复拼进输入流。

显式 `GenerateCredentials` 或 `init --generate-passphrase-file` 创建新的随机口令文件时不提示手工输入，不覆盖已有文件，也不作为来源读取失败后的回退。这是已确认的便携初始化流程，不改变已有口令加密模式。

更换口令必须先验证旧口令。来源冲突、读取失败、口令文本无效、新口令确认不一致或旧口令验证失败，均不改动原 vault；文件写入阶段的跨平台替换和故障保证仍由文件操作契约确定。

更换的是当前 vault 的解锁口令，不是 vault 内保存的业务密码或 API key。旧副本仍能用旧口令解锁，不提供远程撤销或忘记口令后的恢复。

CLI 与 Go 库不把口令写入 vault、导出数据、日志或命令行参数。可编辑的 `Vault` 可在本进程内保留本次显式提供的解锁材料以供保存，调用方控制对象寿命；不建立跨进程托管，也不承诺已解锁进程内所有明文副本都不可提取或必然被擦除。

### 已确认的边界示例

| 场景 | 结果 |
| --- | --- |
| 同一份口令同时选择文件和标准输入 | 报错，不设置来源优先级或回退 |
| 无交互终端，且未指定口令来源 | 直接失败，不阻塞等待输入 |
| 配置值与口令都要求使用标准输入 | 报错；为其中一份输入选择其他来源 |
| 更换口令时旧、新口令都来自标准输入 | 报错，不按两行口令进行复用 |
| CLI 读取文件内容为 `secret`、`secret\n` 或 `secret\r\n` | 三者都表示口令 `secret` |
| CLI 读取文件内容为 ` secret \r\n` | 保留首尾空格，实际口令为 ` secret ` |
| 文件含额外换行、BOM、NUL、无效 UTF-8，或去掉行结束符后为空 | 拒绝，不静默修正内容 |
| 直接把 `secret\n` 作为实际口令内容交给解锁核心 | 拒绝；只有显式文件或标准输入适配器处理行结束符 |
| 新口令两次输入不同，或旧口令验证失败 | 原 vault 不变 |
| 自动化显式提供新口令 | 读取一次，不弹出第二次确认提示 |
| 更换口令后，另一主机保留旧 vault 副本 | 旧副本仍可用旧口令解锁；业务凭据未因此更换 |

表中 `\n` 和 `\r\n` 表示实际行结束符，而非反斜杠字符。以上是用户确认的规格示例，不表示产品测试已经执行。本票没有选择密码算法或新增实现任务；已有密码协议、文件操作和接口票据承接相应细节，地图的其他迷雾保留。
